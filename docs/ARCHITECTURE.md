# 拆分架构评估

结论：将 SSH MCP 从 AI 平台独立出来是合理的。凭据、主机身份和执行权限集中在 SSH 服务；模型只得到有界的诊断结果。Zabbix 与 SSH 是两个独立的数据来源，不应互相代替。

| 组件 | 负责 | 持有的敏感配置 |
| --- | --- | --- |
| AI Ops Platform | 告警、证据缺口判断、任务预算、工具编排、报告、飞书通知 | 模型密钥、两个 MCP 的独立客户端令牌 |
| Zabbix MCP | Zabbix 主机、监控项、历史指标、事件 | Zabbix API 凭据 |
| SSH MCP | 主机登记/分组、跳板、私钥、公钥核验、固定诊断、任务审计 | SSH 私钥、主机身份基线、飞书管理登录配置 |
| Linux 目标 | 接受授权 SSH 账号的受控诊断 | authorized_keys、服务器自身主机密钥 |

## 当前实现适用范围

- 一个服务实例，FastAPI Web 与 Streamable HTTP MCP 共用 9099；两种身份认证独立。
- SQLite 保存资产、授权、任务及审计；私钥和诊断请求/结果经 Fernet 加密。数据库备份必须包含 `master.key`。
- Web 诊断使用 4 个后台线程，SSH 执行器再限制总并发 4、同一主机 1；MCP 同步调用也受执行器限制。最多 200 个 queued/running 任务，单批 100 台。
- 公钥扫描有独立队列，最多 3 个排队/运行批次，每批 1000 台、批内 4 并发。公钥扫描和诊断各有独立并发上限，因此合计可能超过 4 条 SSH 连接。
- 进度与历史可跨页面刷新读取，但线程不是分布式队列。重启后未完成任务明确失败，不会暗中重放命令。
- 每个 MCP 客户端可限定主机组和动作；主机列表及映射同样受范围约束。Web 管理员仍为全权限管理员，这不是完整组织/租户 RBAC。

这适合单一运维团队、分批管理大量登记资产；“可登记 1000 台”不代表可同时执行 1000 个诊断。不要设置 `uvicorn --workers 2`、多个共享卷副本或热重载部署：初始化会处理遗留任务，进程内限流也无法跨副本协调。

## 后续规模扩展条件

如果出现多租户、跨机房调度、任务积压或高可用需求，再拆出执行 Worker，引入持久消息队列、集中数据库、租约/心跳与全局并发控制。此时再将 Web 与 Worker 独立部署；仅增加 Web 副本不会带来安全的执行扩容。

多机房可以先部署多个独立 SSH MCP 实例，AI 平台按固定资产路由选择实例；各自使用独立令牌、私钥和身份基线。模型不能自由选择实例 URL 或目标 IP。

## 本轮修复的重要问题

原脱敏正则将单词边界写成了字面反斜线，典型 password/token 未被遮盖；原主机公钥校验只检查文本样式；原公钥扫描建立 TCP 连接缺少明确连接超时。v0.2 修复这些问题，并增加真实公钥解析、原子密钥文件写入、数据库私有权限、主机版本检查和 OAuth state 原子消费。

安全仍依赖部署网络、飞书管理员和 SSH 授权。固定读命令、返回脱敏和加密存储是多层约束；root 账号仍具有实际 root 权限，程序不会把它变成操作系统层面的只读账户。
