# 三项目工程规范

适用于 AI Ops Platform、SSH MCP Server、日志分析平台。三者**独立部署、独立故障域、独立发版**，通过 MCP 协议协作。本文件在三个仓库中保持一致；仓库自身的约定写在各自的 `AGENTS.md`。

## 1. 职责边界

| 系统 | 负责 | 不负责 |
| --- | --- | --- |
| AI Ops Platform | 告警接入、飞书交互、任务调度与预算、MCP 连接与能力发现、证据存储与引用核对、报告渲染、Skill 管理 | SSH 连接与命令、日志采集与存储、主机凭据 |
| SSH MCP Server | Linux 资产与凭据、主机身份解析、只读诊断脚本与解析、现场实时状态、诊断任务与审计 | AI 编排、历史日志检索与聚合 |
| 日志分析平台 | 集中采集、存储、检索、聚合（OS / 网络设备 / Nginx / Java / 流量）、日志来源管理 | 现场命令执行、AI 编排 |
| Zabbix MCP（外部） | 监控项、历史、趋势、事件、主机信息 | — |

- 实时现场状态（进程、服务、监听、当前日志尾部）走 SSH MCP；告警时刻前后、跨主机、网络设备与长窗口的日志走日志平台。两边对同一现象的分类规则应保持同名同义。
- 不跨项目直接读写对方数据库；只通过 MCP 工具或对方公开的 HTTP API。

## 2. 诊断职责分工（平台代码 / Skill / 模型）

- **平台代码强制**：授权与只读边界、参数校验、预算（轮次、调用次数、Token、时间）与超时、并发、证据编号与引用核对、能力说明与覆盖率（coverage）、输出格式与渲染、脱敏。这些不能只写在 Skill 或提示词里。
- **Skill 声明**：按设备类型与告警类型的诊断策略、预采集清单（prefetch）、证据优先级、补查步骤、解读规则。同一条诊断规则只写一处，不在 Python、Skill、系统提示词里各写一份。
- **模型负责**：理解问题、判断证据是否充分、在授权范围内选择补查、区分事实/推断/待验证假设、给出结论与建议。

## 3. MCP 接口契约

- 工具名、参数、返回字段**只增不改**。删除字段或改变含义＝不兼容变更：升主版本（或次版本并在发布说明中醒目标注），提供迁移说明，并先让调用方兼容新旧两种形态。
- 调用方用**能力发现**判断能用什么：`tools/list` 的工具与 `inputSchema`、`*_list_tool_catalog` 的授权目录与参数范围。不要在调用方写版本号比较。新增可选参数（例如 `ssh_collect` 的 `timeout_seconds`）由调用方在 Schema 中看到后才传。
- 结果统一包含 `status`（success / partial / failed / cancelled）；失败给稳定的 `error_code` 与中文 `error`。常用错误码：`forbidden`（无权限）、`unavailable`（不存在或不可用）、`not_ready`、`not_linux`、`mapping_unresolved`、`busy`、`timeout`、`invalid_argument`、`query_failed`；可以附 `reason`、`retryable` 细分。
- 主机缺少采集前提（未装 nginx、内核未开 PSI、无 journal 权限）用 `CAPABILITY_MISSING:<名称>` + 退出码 69 表示：这是能力说明，不是诊断缺口。
- 截断、抽样、窗口不全都要在结果中标明（`truncated`、`limit_reached`、`hints` 或 `coverage` 说明），调用方据此告诉模型和读者。
- 契约由 `tests/joint/`（AI Ops Platform）用真实服务验证：工具存在且只读、授权目录与推荐授权覆盖平台 Skill 的引用、失败形态可分类。改动 MCP 工具时同时跑它。

## 4. 主机身份

- Zabbix Host ID 是告警的主键；SSH 资产只按 Zabbix Host ID 或已登记 IP **精确**解析（`ssh_resolve_host` / `ssh_resolve_target`），解析结果的 host_id 与 revision 在一次任务内固定，调用时带 `expected_revision`。
- 日志来源按 IP 或主机名精确定位（`log_resolve_target`），有多个匹配时说明歧义，不合并。
- 不靠名称相似或猜测匹配；歧义时停止该来源并在报告“能力说明”中写明原因。

## 5. 降级与报告

- 单个数据源不可用、超时或无权限，不让整个任务失败；已取得的证据保留，并在报告中写明实际数据来源与限制（能力说明、诊断不足、覆盖率）。
- 区分：超时、权限不足、数据为空、服务不可用、主机不具备能力、模型调用参数错误。只有“应取得而未取得的证据”算诊断缺口。

## 6. 代码与变更

- 先找再写：改动前在三个仓库里搜索同类实现，能复用就复用；三处都要的前端组件放进共享 ui-kit（见 `docs/UI-GUIDELINES.md`）。
- 一个 PR 只做一类变更：结构移动 / 去重重构 / 行为变化 / UI / 文档。删除代码前确认生产调用、跨项目依赖、历史数据兼容、迁移与动态引用。
- 每个修复带回归测试；跨项目接口改动带契约测试；数据库改动只能是幂等迁移，并写明回滚影响。
- 提交前：`ruff format`、`ruff check`、`pytest`（各仓库 CI 的同名命令）；前端 `node --check`。
- 仓库公开：不写真实内网 IP、主机名、令牌；示例用 `192.0.2.x`、`198.51.100.x`、`10.x`。

## 7. 发布与升级

- 版本号与 CHANGELOG（“未发布”一节）随功能 PR 更新；发布 PR 只改版本号与发布说明。
- 每个版本在 `UPGRADING`（或发布说明）写：备份要求、迁移、配置兼容、回滚方法。
- 跨项目升级顺序：**先升级被调用方（SSH MCP、日志平台），再升级 AI Ops Platform**；调用方对新旧被调用方都能工作（能力发现）。
